_6 commits (`f9d25d6` M4 closure, then `0fb5ece` T1, `33a2504` T2, `aa7e74d` T3, `0a5c852` T4, `a521cd2` T5) · 199 files · reviewed 2026-10-06_

## Summary

M5 delivers driver onboarding end to end. It includes a contract-first spec (`onboarding-v1.yaml`), a V6 schema that enforces the main invariants in the database (one active vehicle, one open review per driver, one approved and one open document per slot, the suspension-reason CHECK), and a backend that follows the contract. In the backend, the state machine is centralised, every admin endpoint carries the permission named in the contract, and concurrent decisions are serialised by optimistic locks, which the tests verify with real simultaneous requests. The driver app gets an 8-step wizard, a stage tracker, flagged-item resubmission, vehicle switch and renewal. The admin app gets three permission-gated review queues with re-minted secure URLs. A Damascus demo-driver seeder is added. The private-file design meets NFR-S2: types come from magic bytes, storage keys are generated by the server, and files are served only through HMAC-signed tokens that expire, are minted only after a permission check and carry a signed content type. Invalid tokens all return the same 404. I found no Critical or High issues. There is one Warning: the daily expiry job runs as a single transaction and is not isolated from concurrent renewal or switch decisions. A conflict can roll back a whole day's pass. Worse, a driver whose renewal is approved during the run can be left suspended, and nothing lifts that suspension.

## Warning

**W1 — Expiry job is one transaction with no isolation from concurrent decisions: one conflict rolls back the day's pass, and a renewal approved during the run can leave a driver permanently suspended**
- Category: correctness · Severity: Warning · Certainty: Medium (reasoned from the code; not reproduced by a test)
- Location: `backend/src/main/java/com/labby/backend/service/DocumentExpiryServiceImpl.java:153-202` (class-level `@Transactional`, single loop); `DriverRoleServiceImpl.java:371-384` (`suspendForExpiredDocument` does not re-check); `DriverDocumentServiceImpl.java:150-165` (`approveRenewal`); `model/RoleAssignment.java` (no `@Version`)
- Rationale:
  - **(a) Whole-pass rollback.** `runExpiryCheck` loads every current document expiring within 30 days and sets `reminder7SentAt`/`reminder30SentAt` on the managed `DriverDocument` entities, which are `@Version`ed. These changes are flushed only at commit. If an admin approves a renewal of one of those documents in the meantime (`approveRenewal` marks it `superseded` and bumps its version), the job's commit fails with an optimistic-lock error. That rolls back the entire pass: every reminder and every suspension for every driver. Nothing retries until the next day's cron. Renewals of documents inside the 30-day window are exactly the ones being decided, so this is the normal case for a collision, though the timing window (around 00:05 local) is narrow.
  - **(b) Stuck suspension.** The job decides who to suspend from a snapshot taken when it reads the documents. It then calls `suspendForExpiredDocument`, which only checks `state == ACTIVE` and never re-checks for expired current documents. Suppose `approveRenewal` commits between the job's read and its role update. At that point `reinstateIfNoExpiredDocument` sees an ACTIVE role and does nothing, and then the job suspends the driver. The driver now holds a valid approved document but is suspended with `document_expired`. Nothing ever reinstates them, because only renewal or switch approval calls `reinstateIfNoExpiredDocument` and the job never lifts suspensions. `RoleAssignment` has no version or lock that would serialise the two writers. This breaks DRV-04's "suspends until a renewed document is approved".
- Fix Suggestion: Process each driver (its reminders plus its suspension) in its own transaction (`REQUIRES_NEW`, or a per-driver service call from the job) so one conflict costs only that driver. In `suspendForExpiredDocument`, take a pessimistic lock on the role assignment (`@Lock(PESSIMISTIC_WRITE)` finder) and re-check `hasExpiredCurrentDocument` against fresh data before suspending. Have `approveRenewal` and `approveSwitch` take the same role lock before superseding or activating, so the two orderings serialise. Optionally the job could also reinstate `document_expired` suspensions with nothing expired (self-healing), but that extends the contract's "approval lifts" rule and needs the owner's OK. Add a clock-controlled test that approves a renewal between the job's read and its suspend (or injects a version bump) and asserts the driver ends up active.

## Info (max 5)

1. **A renewal pending on the old vehicle survives a vehicle switch.** `DriverVehicleServiceImpl.approveSwitch` (`:183-200`) deactivates the old vehicle but leaves that vehicle's open registration or insurance renewal `pending`. `findPendingRenewals` (`DriverDocumentRepository.java:59-77`) still lists it, because its approved sibling on the inactive vehicle still exists. The admin queue therefore shows a renewal for a vehicle the driver no longer uses, the driver no longer sees it (`listSlots` covers only the active vehicle), and approving it changes nothing. Consider closing the old vehicle's open renewals (as `rejected` with a system note) when a switch is approved, or excluding inactive vehicles from the renewal queue.
2. **`STORAGE_DRIVER_FILE_MAX_BYTES` can only be lowered.** The multipart limit is fixed at `max-file-size: 10MB` / `max-request-size: 11MB` (`application.yml:18-19`), so raising the new env var (`application.yml:78`, documented in `.env.example`) above 10 MiB has no effect. Either derive the multipart limits from the same property or document the ceiling in `.env.example`.
3. **Uploads have no quota and orphans are never collected.** Any authenticated account can `POST /api/v1/driver/files` (`DriverFilesController.java:119-126`) without limit. Bytes are written before the `stored_files` row (`DriverFileServiceImpl.java:58-69`), and unreferenced uploads are never cleaned up, which is a disk-exhaustion vector for any registered user. Product call for the owner (quota or rate limit and an orphan sweep); not in the SRS today.
4. **Applications of soft-deleted accounts stay in the queue and can be approved.** `listApplications`/`approve` (`DriverApplicationServiceImpl.java:226-250, 345-408`) never look at `users.state`. An applicant who deletes their account (UC-S-07) stays in the reviewer's queue, and approving them grants a driver role to a DELETED account. Low impact in the 30-day reactivation window; an owner ruling is wanted (hide, or 409 on decide).
5. **Driver README not updated for the new screens.** `apps/driver/README.md` is untouched in the range, while `apps/admin/README.md` documents its new queues. The tracker already records this as a known gap; close it with the M5 closure.

## What's good

- **NFR-S2 is designed, not bolted on.** Types are detected from magic bytes and the client header is ignored (`FileSignatures`). Storage keys are generated by the server, so no client input reaches the path. The token's signed payload includes the content type, so a token cannot be replayed as another media type, and `nosniff`/`no-store` are set. Every invalid token returns the same plain 404, and there is a separate test for "signed token, missing file". The HMAC key is domain-separated from the JWT key.
- **Database invariants do the heavy lifting.** Partial unique indexes enforce one active vehicle, one open review and, per slot, one approved plus one open document (`NULLS NOT DISTINCT` for the vehicle-less ID and licence slots). CHECKs tie `active ⇒ approved`, the rejection reason to the `rejected` status, and the suspension reason to the `suspended` state. `OnboardingPersistence.saveAndFlush` turns the resulting violations into 409 at the point of the race.
- **Race tests are real races.** `simultaneously(...)` releases concurrent HTTP calls with a latch. Every decision path (application approve‖approve and approve‖reject, switch approve‖reject, renewal approve‖reject, simultaneous switch submissions) asserts exactly one winner, and the application race also checks that exactly one history event exists.
- **The contract and the code match in all three places.** Every backend DTO matches its schema in `onboarding-v1.yaml` field for field (checked: `DriverApplication`, `AdminDriverApplication` via `@JsonUnwrapped`, `VehicleWithDocuments`, `DocumentSlot`, `DocumentRenewal`, `ExpiryRow`, `VehicleReview`, request bodies). Enum wire values match through `@JsonValue`. The driver (`onboarding-types.ts`) and admin (`api/onboarding.ts`) type mirrors match those DTOs, including the nullable and optional fields, the `image/webp` profile photo, and `suspensionReason` in `auth-v1.yaml`.
- **i18n and RTL hygiene.** EN and AR are in exact key parity in both apps (admin 518/518, driver 301/301, plus a parity test in the driver app). Every static `t()` key used by the new code exists. The new CSS and RN styles contain no physical left/right properties, plates render with `dir="auto"`, and both apps have an Arabic RTL render test.
